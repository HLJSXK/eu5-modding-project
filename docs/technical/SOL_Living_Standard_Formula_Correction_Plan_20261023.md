# 生活水平公式修正计划（2026-10-23）

状态：已实施并通过离线验证，游戏内验收待完成。修正对象是提交 `c16ca48e 分离生活水平与购买力`。
该提交的设计说明是 `SOL_Living_Standard_Purchasing_Power_Separation_20261023.md`。之后的 `8fe79b38` 和 `ae003af4` 两个提交没有读取生活水平变量，只有 `8fe79b38` 在文档里转述了旧定义。

## 1. 正确定义

```
生活水平 SOL = 千人均年流动资金 + 生活水平修正
购买力   PP  = 千人均年流动资金 ÷ 千人均年基准消费
```

| 项 | 单位 | 在现有代码里怎么得到 |
|---|---|---|
| 千人均年流动资金 | 金 / 千人 / 年 | `sol_location_<e>_liquid_funds`（月度）× 12 ÷ 该阶层人口（千人） |
| 千人均年基准消费 | 金 / 千人 / 年 | `sol_location_<e>_base_spending`（月度）× 12 ÷ 该阶层人口 |
| 生活水平修正 | 金当量 / 千人 / 年 | 新钩子，目前为 0 |
| 生活水平 | 一个数，单位同上 | 不是比值，也不是百分数 |
| 购买力 | 比值，1 = 刚好买得起基准篮子 | 界面显示为 比值 − 1 的百分数 |

两者的关系：修正为 0 时，生活水平 = 购买力 × 千人均年基准消费。原需求里说的"一对一换算"，指的是乘一个换算系数（基准消费）。基准消费随阶层、随地点（替代组）变化，所以修正为 0 时生活水平也不等于购买力。

**购买力不需要改。** 现在的 `sol_location_raw_demand_scale = liquid_funds ÷ base_total_spending` 是两个同为月度、同一批人口的总量相除。它和"千人均年流动资金 ÷ 千人均年基准消费"在数学上是同一个数。需求、求解器和 `local_pop_demand` 修正都不动。

### 算例

某地点有 2 千农民，月流动资金 0.3 金，基准消费 0.1 金/千人/月；另有 0.05 千贵族，月流动资金 0.4 金，基准消费 4 金/千人/月。

| | 购买力 | 生活水平（现在写错的） | 生活水平（正确） |
|---|---|---|---|
| 农民 | 0.3 ÷ 0.2 = 1.5（+50%） | 1.5（显示 +50%） | 0.3 × 12 ÷ 2 = **1.8** |
| 贵族 | 0.4 ÷ 0.2 = 2.0（+100%） | 2.0（显示 +100%） | 0.4 × 12 ÷ 0.05 = **96** |
| 贵族 ÷ 农民 | 1.33 倍 | 1.33 倍 | **53 倍** |
| 修正 +3 之后的农民 | 1.5（不变） | — | **4.8** |

## 2. 错误回顾

### 2.1 写成了什么

`scripts/sol_living_standard_source.py` 把生活水平定义成 **购买力 + 以基准篮子计的加成**，存为比值，显示为 比值 − 1：

```
sol_location_<e>_sol_equivalent = max(0, liquid_funds_<e> + bonus_<e> × base_spending_<e>)
sol_ls_sol[_<e>]                = Σ sol_equivalent ÷ Σ base_spending
```

这导致三处偏差：

1. **量纲错。** 生活水平被写成了"基准篮子的倍数"，所以修正为 0 时生活水平恒等于购买力。实际上它应该是"每千人每年的金额"。
2. **加权错。** 汇总时用基准消费做权重，正确做法是按人口加权。基准篮子贵的阶层和地点因此被放大。没有基准篮子的人（原版部落民）连生活水平都算不出来。
3. **加成的含义错。** 原来的 `bonus = 0.1` 表示 +10 个百分点，并且要乘基准消费。正确的修正应该是直接加在每千人每年金额上的一个数。

### 2.2 怎么发生的

1. **把"一对一换算"读成了"相等"。** 原需求原话是"它在当前版本和购买力是一对一换算关系"。实现时理解成了"现在 SOL 就是 PP"，没有追问换算系数是什么、生活水平的单位是什么。当时用 AskUserQuestion 只问了哪些界面显示哪个数，没有确认公式本身。
2. **删掉了本来对的东西。** 拆分前，"SOL生活水平"地图和情势地图读的是 `gls_location_actual_per_capita_spending = sol_location_liquid_funds ÷ local_sol_total_population`，也就是千人均月流动资金，阈值 0.5 / 0.1。顶栏等级和排行读的是人均收入（金/千人/年，`|2 @gold!`）。这些都是"人均金额"型的度量，离正确定义只差 ×12 和修正项。拆分时它们被判为"名不副实"，删除后换成了比值。项目里对"生活水平"本来有两种互相矛盾的用法：面板上是比值，地图和排行上是人均金额。遇到这种矛盾应该停下来问用户，当时没有问，而是自己选了其中一种。
3. **测试把误解固化了。** `test_zero_bonus_equals_purchasing_power` 断言的正是错误的定义，所以 110 项测试全部通过，只说明代码和这份错误的说明书一致。设计说明、`anti_patterns.yaml`、`PROJECT_OVERVIEW.md`、BRIEF、CHANGELOG 和记忆文件都抄了同一份错误定义，后续会话读到的都是"生活水平 = 购买力 + 加成"。
4. **出现过反常信号，但没有被当成问题。** 部落民因为基准消费为 0 而失去生活水平、退出排名；修正为 0 时生活水平和购买力逐位相等，"分离"在数值上什么也没分开；标题上出现"低 +40%"这种自相矛盾的显示。这几条都被当作"副作用"写进了说明，没有回头怀疑定义。

## 3. 修正方案

### 3.1 新的计算口径

用 `P_e` 表示阶层人口（千人），口径与收入累加器一致：贵族、教士、市民、部落民用 `num_pop_type:<e>`，平民用 `local_commoner_population`，全体用 `local_sol_population_sum`。`LF_e` 是月流动资金，`M_e` 是修正。

```
地点、阶层：sol_location_<e>_sol_total = max(0, LF_e × 12 + M_e × P_e)     # 年度"生活水平总量"，不是可花的钱
地点合计：  sol_location_sol_total     = Σ_e sol_location_<e>_sol_total
地点数值：  sol_location_sol           = sol_location_sol_total ÷ local_sol_population_sum   （人口为 0 时不设）
国家/阶层： sol_ls_sol[_<e>]           = Σ_地点 sol_total ÷ Σ_地点 P_e                     （人口为 0 时不设）
世界平均：  sol_ls_world_sol[_<e>]     = 各国生活水平按人口加权（排行逻辑原样，现在恰好等于世界总量 ÷ 世界人口）
```

`max(0, …)` 是否保留取决于决策 2。×12 复用 `sol_ls_annualization_factor`，不另写常数。

### 3.2 改名

单位变了。如果名字不变，旧写法会静默算出错数，例如有人照旧写 `bonus = 0.1` 想加 10%。改名能让漏改的地方直接报错。

| 旧 | 新 | 说明 |
|---|---|---|
| `sol_location_local_sol_bonus_value` | `sol_location_local_sol_modifier_value` | 修正，单位：金当量/千人/年 |
| `sol_location_<e>_local_sol_bonus_value` | `sol_location_<e>_local_sol_modifier_value` | 分阶层，默认取通用值 |
| `sol_location_<e>_sol_equivalent` / `sol_location_sol_equivalent` | `sol_location_<e>_sol_total` / `sol_location_sol_total` | 年度总量 |
| — | `sol_location_sol` | 地点生活水平数值，供地图和情势 |
| `sol_ls_sol_equivalent_<m>` / `sol_ls_sol_base_<m>` | `sol_ls_sol_total_<m>`；分母复用 `sol_ls_pop_<m>` | 见 3.3 第 1 步 |
| `sol_ls_sol_index_display` | `sol_ls_sol_display` | 数值本身，未计算时为 0 |
| `sol_ls_sol[_<e>]`、`sol_ls_world_sol*`、`sol_ls_top_sol*` | 名字不变 | 含义变成数值；第 5 步加测试，禁止它们再配 `%` 格式或 `Subtract … 1` |

## 4. 需要你拍板的问题

**决策 1：修正从哪里来。** 修正暂时还是脚本里的数值钩子，下一步做建筑时再改成真正的游戏修正。真正的修正指像"当地生活水平 +3"这样挂在建筑或事件上、在原版修正提示里能看到的那种，它要新定义修正类型，并在脚本值里读出来，属于必须先查原版写法（Step 2/3）的类别。这次修公式不需要先定这个。
建议：这次只修公式，并把钩子改名为"修正"。

**决策 2：修正为负时能不能把生活水平压到 0 以下。** 举例：瘟疫给 −5，一个只有 1.8 的农民地点会变成 −3.2。可以选"最低按 0 算"，也可以"允许负数，表示比一无所有还糟"。
建议：先按 0 封底，和现在一致。排行进度条和分档都默认数值不为负，允许负数需要另改这两处。

**决策 3：生活水平地图怎么上色。** 原来的地图以"刚好买得起基准篮子"作为中间的黄色，现在生活水平是金额，没有这个天然的零点了。有三种做法：
 (a) 跟世界平均比：0 是红，世界平均是黄，世界平均的 3 倍是绿。全游戏 300 年里经济规模会变，这种做法颜色始终有对比，缺点是每年 1 月 1 日排行刷新时整体颜色会跳一次，开局排行出来之前也需要一个兜底值。
 (b) 固定金额：比如拆分前用的每千人每月 0.5 金，折合每年 6 金算"很高"。直观，但几百年后可能全图都是绿的。
 (c) 跟本地基准消费比：修正为 0 时，它和购买力地图会一模一样，失去意义。
建议：选 (a)。tooltip 分档同样相对世界平均，例如"≥ 2 倍很高、≥ 1 倍中等、≥ 0.5 倍较低、以下很低"。顶栏等级本来就是这样相对世界平均分的，两处口径一致。

**决策 4：数字怎么写。** 例如"生活水平：中 18.0"。要不要带金币图标？带图标直观，但等修正有了建筑来源，这个数就不全是钱了。
建议：不带金币图标，在 tooltip 脚注里写清"每千人每年"和公式。

## 7. 防止再犯

- 需求里出现"换算""对应""等价"这类词时，先用一句话加一个带数字的算例复述公式，问清单位和系数，再动手。
- 同一个概念在项目里有两种互相矛盾的实现时（这次是面板上的比值和地图上的人均金额），把两种都摆给用户选，不自己挑一种然后删掉另一种。
- 测试至少要有一个"新定义和旧定义会给出不同结果"的用例（这次就是"改篮子，生活水平不变"）。只断言"新值等于旧值"的测试证明不了分离做对了。
