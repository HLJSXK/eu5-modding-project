# EU5 多 Mod 兼容与加载规则

> 记录日期：2026-07-21  
> 来源：用户提供的 EU5 compatibility mechanics 说明。  
> 适用范围：大多数游戏数据库文件；具体目录是否支持数据库操作关键字，仍需查阅当前版本的官方类型定义或原版文件。

## 核心判断顺序

分析两个 Mod 是否冲突时，按以下顺序判断：

1. 是否存在完全相同相对路径和文件名的文件。若存在，先按“整文件覆盖”规则选出唯一生效文件。
2. 若文件都能进入数据库加载器，检查它们是否修改同一个顶层对象 key。
3. 对同一对象的修改，先比较数据库操作类型，再比较文件加载顺序。
4. 最后检查注入内容本身能否叠加，例如字段是否允许重复、触发器或效果块是否已经存在。

最重要的结论是：

> 文件名或播放列表顺序不是所有冲突的最高优先级。不同数据库操作类型冲突时，固定的操作处理顺序优先；只有操作类型相同时，才由文件名顺序决定先后。

## 1. 文件加载顺序

- 文件按 ASCII 顺序加载，例如 `00_foo.txt` 早于 `01_bar.txt`。
- 这个排序不区分文件来自原版、DLC 还是 Mod。
- 父目录中的文件先于子目录中的文件。比如 `events/zz_example.txt` 仍早于 `events/example/00_example.txt`；不能只比较 basename。
- 普通顶层对象按定义出现的顺序加载。多数情况下这不改变玩法，但可能改变相关界面中的显示顺序。

文件名前缀适合控制同类操作之间的顺序，也适合避免文件名碰撞，但不能跨越下文的操作类型优先级。

## 2. 完全同路径的整文件覆盖

当两个来源包含完全相同相对路径和文件名的文件时，会发生直接文件覆盖：

- Mod 文件优先于原版或 DLC 文件。
- 多个 Mod 冲突时，播放列表中位置更低的 Mod 文件优先。
- 只有最高优先级文件会被使用，其他同路径文件等同于不存在。

这与“多个不同文件共同修改同一数据库对象”不是同一种机制。兼容性扫描必须把两者分开报告。

## 3. 数据库对象操作关键字

这些关键字只能用于文件中的顶层对象，不能放在对象内部的子块上。

| 关键字 | 对象存在时 | 对象不存在时 |
| --- | --- | --- |
| `INJECT:` | 在现有对象末尾追加脚本 | 报错 |
| `REPLACE:` | 用新定义替换现有对象 | 报错 |
| `TRY_INJECT:` | 与 `INJECT:` 相同 | 跳过，不报错 |
| `TRY_REPLACE:` | 与 `REPLACE:` 相同 | 跳过，不报错 |
| `INJECT_OR_CREATE:` | 与 `INJECT:` 相同 | 创建对象 |
| `REPLACE_OR_CREATE:` | 与 `REPLACE:` 相同 | 创建对象 |

合法形式：

```text
INJECT:building_example = {
    possible_production_methods = {
        foo
    }
}
```

非法形式：

```text
building_example = {
    INJECT:possible_production_methods = {
        foo
    }
}
```

因此，目标改动位于不可独立寻址的子块时，通常无法只靠 `INJECT:` 精确修改。

## 4. 固定的操作处理顺序

数据库先按操作类型分批处理，再在同一操作类型内按文件名处理。顺序从早到晚为：

```text
INJECT_OR_CREATE
-> REPLACE_OR_CREATE
-> TRY_INJECT
-> TRY_REPLACE
-> INJECT
-> REPLACE
```

后处理的操作能够覆盖早处理操作产生的结果。因此：

- 两个文件都使用 `TRY_REPLACE:` 修改同一 key 时，较晚的文件名获胜。
- `REPLACE:` 总在 `REPLACE_OR_CREATE:` 之后处理，所以前者获胜，与双方文件名无关。
- `TRY_INJECT:` 或 `INJECT:` 的结果可能被之后处理的 `REPLACE:` 整体抹掉；把注入文件改名为 `zz_...` 也无法避免。
- `REPLACE_OR_CREATE:` 先于注入操作处理，因此之后的 `TRY_INJECT:` 或 `INJECT:` 仍可追加到它创建或替换的对象上。

也就是说，兼容补丁不能只依赖 `zz_` 文件名。它必须选择能够实现目标的操作类型，并同时考虑目标对象可能不存在时的报错行为。

## 5. `INJECT` 的合并边界

`INJECT:` 是把脚本追加到对象定义末尾，并不保证对内部结构进行深度合并。

如果原对象已有一个可重复的子块，注入同名子块后，结果通常是对象内出现第二个同名子块，而不是把新内容插入旧子块。例如注入第二个 `wargoal_scores` 后，最终对象会同时包含两个 `wargoal_scores` 块。引擎如何解释重复元素取决于该数据类型：可能覆盖、叠加，也可能不读取其中一部分。

还需特别注意：

- 多数 trigger/effect 字段已经存在时，不能通过再次注入同名字段来可靠合并；若原对象没有该字段，注入一个新字段才可能正常工作。
- 对 scripted effects 和 scripted triggers 使用 `INJECT:` 不会追加其内部效果或条件，而会像 `REPLACE:` 一样覆盖原定义。
- 并非所有数据库目录都支持这些关键字。使用前应查当前版本的 `reference_official_defines/`，不足时再查 `reference_game_files/`。

## 6. 多 Mod 兼容检查清单

1. 扫描完全相同的相对路径，确定是否发生整文件覆盖。
2. 扫描不同文件中重复的顶层对象 key。
3. 为每个重复 key 记录双方使用的操作类型，不要只记录文件名。
4. 先套用固定操作顺序；仅在操作类型相同时比较完整相对路径的加载顺序。
5. 检查父目录与子目录关系，不能只比较文件 basename。
6. 对 `INJECT:` 检查目标字段是否允许重复，以及是否涉及 trigger/effect、scripted effect 或 scripted trigger。
7. 设计兼容补丁时，明确最终对象应是替换、追加还是条件创建；不要把 `zz_` 当作万能覆盖手段。
8. 最后进行联合加载和 `error.log` 检查，因为重复子块的实际解释仍由具体数据库类型决定。
